# Hyperliquid 接口自动化测试开发课程 V2

## 一、学习背景与当前进度

### 1. 学习目标

围绕 Hyperliquid 接口和 Python 开源 SDK，逐步构建一套：

- 默认安全、环境隔离的接口测试框架；
- 支持离线单元测试与真实接口集成测试；
- 具备公共断言、配置、超时、异常、Mock、Schema 校验；
- 能处理动态行情、异步状态、重试、限流和并行隔离；
- 能在 **testnet** 完成受控的下单、查单、撤单链路；
- 能进入 CI，生成报告、推送告警；
- 能解释架构设计、验证测试可信度，并形成可展示项目。

**目标不是开发交易策略，不是追求收益，也不是制造一个功能堆叠的“万能框架”。**

## 二、项目边界：先明确我们在测试什么

### 1. 默认练习对象

本课程默认使用：

- [Hyperliquid 官方 Python SDK](https://github.com/hyperliquid-dex/hyperliquid-python-sdk)
- [Hyperliquid 官方 API 文档](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api)

如果学习者实际使用的是其他 Hyperliquid 开源项目，应先确认仓库和版本，再调整课程实例。

官方仓库是 **API 客户端 SDK**，包含 `api.py`、`info.py`、`exchange.py`、签名工具、WebSocket 和测试，不应把它当成已经提供完整后端与数据库的服务端项目。[^1][^1]

### 2. 三个不同测试对象

| 测试对象 | 我们能够验证什么 | 不应宣称什么 |
|---|---|---|
| 自己编写的测试框架 | 配置、客户端、断言、异常、重试、清理、报告逻辑 | 不能用它的代码覆盖率代表 Hyperliquid 服务端覆盖率 |
| 官方 Python SDK | 选定方法的行为、参数转换、签名回归、异常表现 | 不能未经验证就声称整个 SDK 正确 |
| Hyperliquid 真实接口 | 公开契约、响应语义、账户状态与交易生命周期 | 不能直接验证不可访问的内部数据库、缓存和服务端实现 |

### 3. 两条调用路径，不混为一谈

| 调用路径 | 用途 | 设计原则 |
|---|---|---|
| 自己的 `ApiClient → InfoApi → /info` | 练习 HTTP 客户端、配置、异常、断言与协议校验 | 延续当前第 10 课成果 |
| 官方 SDK → 自己的轻量适配层 | 练习 SDK 使用、签名交易、WebSocket 与 SDK 回归 | 复用官方能力，不重新实现签名协议 |

**不要因为两者都用了 Requests，就假设它们共享同一个 Session、超时和重试配置。**

当前官方 SDK 的底层 `API` 自己创建 `requests.Session`，`timeout` 默认是 `None`；正常 HTTP 响应的 JSON 解析失败还可能返回一个 `error` 字典。这些行为需要在所选版本中确认和适配。[^2]

### 4. 版本管理原则

首次补课时记录：

- Python 版本；
- SDK 包版本或 Git commit；
- pytest 与相关插件版本；
- 依赖锁定方式；
- 官方文档核对日期。

不凭记忆指定“最新版本”，也不盲目复制上游开发环境。官方 README 的开发说明与 `../pyproject.toml` 中运行时、开发依赖约束并不完全相同，应以实际采用的版本和安装验证为准。[^1][^3]

## 三、整个课程必须遵守的安全与设计原则

| 原则 | 必须落实的要求 |
|---|---|
| 默认离线或只读 | 普通测试命令不得意外执行交易 |
| 默认 testnet | 不把 mainnet 当练习交易环境 |
| mainnet 禁止写操作 | 本课程不提供打开 mainnet 写入的开关 |
| 交易显式授权 | testnet 交易需要单独授权、专用标记和运行时校验 |
| 不能只依赖 `-m` | 写入适配层必须再次检查环境、目标地址和授权条件 |
| 安全规则先落地 | 全部课程之前先加入最小安全边界，后续再深化 |
| 不泄露秘密 | 私钥、签名敏感材料、Webhook 不进入仓库、日志、报告和对话 |
| TLS 验证默认开启 | 不把 `verify=False` 作为客户端默认配置 |
| 网络调用有超时 | 自己的客户端与 SDK 路径分别确认 |
| 不吞断言 | 捕获异常不能把失败转换成通过 |
| 不依赖用例顺序 | 不使用“上一个测试生成数据，下一个测试消费数据”的设计 |
| 按语义决定重试 | 只读 POST 与交易 POST 不采用同一重试政策 |
| 不以重跑制造绿灯 | `rerun` 不替代缺陷定位与稳定性治理 |
| 并行有隔离 | session fixture 不等于跨 worker 全局单例 |
| 有界等待 | 不使用无限轮询，不依赖大量固定 `sleep` |
| 清理有归属 | 只处理本次运行创建、能够确认归属的资源 |
| 不自动清空账户 | 禁止为了清理测试而撤掉全部订单、随意平掉全部仓位 |
| 不压测公开服务 | 限流和性能故障实验放在本地 Mock 或授权环境 |

账户查询与签名身份要分清：API wallet/agent 用来签名，账户查询应使用实际主账户或子账户地址，而不是 agent 地址。[^4]

| 课 | 主题 | 核心知识与 Hyperliquid 练习 | 交付物 / 验收 |

### 第 11 课的特别要求

不要把公共断言库写成另一套庞大的测试框架。

先提取真正重复、语义稳定的校验，例如：

- HTTP 状态校验；
- 必要字段存在；
- 响应对象类型；
- 数值字符串合法性；
- 业务结果中的错误检测。

**业务特有、不重复的断言仍可以留在用例中。**

### 第 18 课的特别要求

Hyperliquid 价格规则不是简单的“保留几位小数”：还涉及有效数字、`szDecimals`、永续与现货不同的小数位上限，以及整数价格例外。应依据官方规则编写边界测试。[^5]

不要默认覆盖所有产品。先聚焦明确选定的基础永续市场，后续再扩展现货或其他市场类型。

## 阶段三：契约、动态数据与稳定性——第 21–29 课

**阶段目标：正确测试动态系统，不用固定值和重跑掩盖状态变化。**

| 课 | 主题 | 核心知识与 Hyperliquid 练习 | 交付物 / 验收 |
|---|---|---|---|
| 21 | Schema 契约校验 | 字段、类型、嵌套、可选项、空数组；按响应版本管理 schema | 关键 `/info` schema；合法空状态不会被误判 |
| 22 | 正反向测试矩阵 | 缺字段、错误类型、无效地址、未知类型；哪些离线验证，哪些真实验证 | 测试矩阵；预期错误语义有依据，不随意猜错误码 |
| 23 | 动态数据与数据工厂 | run ID、唯一标识、固定随机种子、合法/非法数据分离 | 数据工厂；可重现，动态数据不硬编码预期行情 |
| 24 | 只读跨接口一致性 | `meta`、账户状态、订单与成交数据关联；集合与状态约束 | 只读关联用例；明确时间边界和市场范围 |
| 25 | 最终一致性与有界轮询 | deadline、轮询间隔、退避、终态判断、最后观测证据 | 等待工具；超时报告完整，不无限等待 |
| 26 | fixture 生命周期与资源登记 | 创建、登记、使用、清理；准备阶段部分失败；清理异常 | 资源登记器；用假资源证明部分失败也能清理 |
| 27 | 限流、重试与 flaky 治理 | 请求权重、429、退避、抖动、最大预算；只读重试与写入禁止盲重试 | 重试策略；离线验证，公开接口低频运行 |
| 28 | pytest-xdist 与并行隔离 | worker fixture、独立数据、日志冲突、账户和 nonce 隔离 | unit/只读用例并行；交易阶段仍默认串行 |
| 29 | SDK 源码、录制与回放 | 阅读上游测试；cassette、脱敏、回放与实时结果差异 | 一个可回放测试；普通 CI 不自动录制真实数据 |

### 本阶段的关键判断

**跨接口一致性不等于同一瞬间的原子快照。**

例如：

- 连续两次行情查询可能不同；
- 账户未实现盈亏可能随价格变化；
- 订单状态在两个接口查询之间可能已经改变。

所以应优先验证：

- 结构；
- 关联关系；
- 允许的状态集合；
- 时间窗口；
- 有界等待后的状态。

不能要求所有金额和状态在任意时刻完全相等。

Hyperliquid 的 REST 限流有请求权重，并存在单独的地址动作限制，不宜设计成“每个请求都算同样成本”。[^6][^6]

**录制回放能够证明代码对已保存响应的处理能力，不能证明当前线上接口仍然健康。**

## 阶段四：受控交易生命周期——第 30–35 课

**阶段目标：在 testnet 做可解释、可追踪、有清理能力的交易测试。**

进入本阶段前，必须通过：

- 环境与写入闸门测试；
- 超时、异常、精度单元测试；
- 有界轮询测试；
- 资源登记与清理测试；
- 默认不交易的执行验证。

| 课 | 主题 | 核心知识与 Hyperliquid 练习 | 交付物 / 验收 |
|---|---|---|---|
| 30 | 钱包、签名与 nonce | 主账户/agent 区分；签名作用；SDK 签名测试；nonce 冲突 | 签名适配与离线回归；不手写密码学实现 |
| 31 | 交易前置检查与风险预算 | testnet 身份、账户状态、产品范围、余额、规则、名义金额、已有资源 | preflight；条件不满足明确阻断，不进入交易 |
| 32 | 交易响应与订单状态解析 | HTTP 成功≠业务成功；订单错误、挂单、成交、取消；状态机 | 响应解析器；离线覆盖多种订单结果 |
| 33 | cloid 与写入结果不确定性 | 唯一 cloid、oid、提交超时、状态对账；nonce 与幂等区别 | 不确定结果处理；超时后先查询，不自动重复下单 |
| 34 | 下单→查单→撤单闭环 | 动态合法价格数量；受控 ALO；查询、轮询、撤单、确认与清理 | 单个独立场景；不依赖其他测试执行顺序 |
| 35 | 负向交易与故障恢复 | 精度错误、业务拒绝、未知结果、重复清理、部分失败 | 大部分离线，少量受控 testnet 验证；清理不覆盖原始失败 |

### 交易教学的限制

- 只在专用 testnet 账户练习；
- 不把提现、转账、桥接等资产转移操作作为课程必做内容；
- 不让老师在对话中索要私钥；
- 不自动提升杠杆、扩大交易规模来“让测试通过”；
- 没有资金或权限时，保留离线验证并明确说明真实链路未执行；
- live 交易缺少授权可以跳过，但不能把“未执行”宣传为“验证通过”。

官方推荐使用已有 SDK 生成签名，并提醒存在不同签名方案、字段顺序、数字尾零等易错点。[^7]

### 对下单与撤单的正确预期

ALO 是 post-only，避免立即匹配，但**订单挂入订单簿后仍可能成交**，不能把它当成“永远不会成交”的安全保证。[^8]

因此第 34 课要分清：

- 用例预期路径：订单挂单后撤单；
- 非预期但真实可能路径：订单在撤单前成交；
- 不确定路径：提交超时，无法立即确认是否成功。

非预期成交不能为了变绿就当作撤单测试成功，也不能直接全账户平仓。应保留证据，停止后续危险操作，按预先确定的处置方案处理。

`orderStatus` 支持按 oid 或 cloid 查询，但 cloid 的存在不应直接被解释为“任意重试都安全”。[^9]

nonce 按 signer 跟踪，共用 agent 的不同进程或账户活动可能产生冲突，因此交易默认串行、专用身份优先。[^4]

## 阶段五：实时数据与可观测性——第 36–38 课

**阶段目标：补齐 Hyperliquid 项目特有的实时能力，但不从零重写完整网络栈。**

| 课 | 主题 | 核心知识与练习 | 交付物 / 验收 |
|---|---|---|---|
| 36 | WebSocket 订阅与生命周期 | 优先复用 SDK；回调、队列、订阅确认、消息验证、退出清理 | 一个 testnet 只读订阅；有等待期限和退出机制 |
| 37 | 断线、重连与 REST 对账 | 在本地模拟断线、延迟、重复、乱序；按频道理解快照和补偿 | 恢复测试；不假设所有频道都有相同语义 |
| 38 | 失败证据与安全软断言 | run ID、最后响应、轮询轨迹、阶段标签、脱敏、聚合错误 | 失败证据包；前置条件硬断言，独立字段才聚合 |

Hyperliquid 官方提供 testnet WebSocket 入口，并要求自动化客户端处理服务端断开和重连。[^10][^10]

这里不要求第一版就做到全频道、自动重放和完整订单簿重建。先把一个只读频道的生命周期和失败路径做好。

## 阶段六：工程化交付——第 39–44 课

**阶段目标：项目可以从干净环境启动、自动验证，并准确表达质量边界。**

| 课 | 主题 | 核心知识与练习 | 交付物 / 验收 |
|---|---|---|---|
| 39 | 依赖、代码质量与可安装项目 | 项目元数据、锁定依赖、格式化、lint、关键类型、干净安装 | 新环境复现成功；工具规则不与上游项目混乱冲突 |
| 40 | 离线 CI 基线 | GitHub Actions；安装、lint、unit、回放、制品；PR 无交易秘密 | 每次提交触发离线验证；外网波动不影响 unit |
| 41 | 真实接口 CI 分流 | 手动/定时只读；受保护 testnet 交易；Secrets；并发控制 | live job 独立；未授权 PR 不获得交易能力 |
| 42 | Allure 发布与告警 | 报告制品、历史条件、通知汇总、限频、失败分类 | 一次运行一条摘要；告警失败不掩盖测试失败 |
| 43 | 覆盖率与质量门禁 | 框架代码与 SDK 代码范围；分支覆盖；阈值制定；skip 审计 | 门禁有依据；不声称拥有远程服务端代码覆盖率 |
| 44 | 毕业项目与技术表达 | README、架构图、复现步骤、风险说明、缺陷复盘、STAR | 可交付项目；只表达真实测量和实际完成成果 |

### CI 的推荐分流

| 流水线 | 默认触发方式 | 网络与权限 |
|---|---|---|
| 离线质量检查 | commit / PR | 不需要 Hyperliquid 网络与交易秘密 |
| testnet 只读回归 | 手动、低频定时 | 允许访问接口，不需要签名私钥 |
| testnet 交易验证 | 受保护的手动触发 | 专用秘密、显式授权、并发限制 |
| mainnet 只读观察 | 可选、单独授权 | 仅只读，不能借此进入写操作 |

交易 job 不应配置为随意取消正在执行的任务而忽略清理。即使如此，进程被强杀仍可能导致 fixture 清理无法执行，所以需要保存资源归属信息，支持后续人工或受控恢复。

# 五、选修模块：有条件再学，不硬塞进主线

## 为什么数据库和 Redis 改为选修？

在官方公开 API 与 SDK 项目里，不能假定你可以访问 Hyperliquid 的内部数据库和 Redis。

所以数据库、缓存、UI 的学习应通过**自建练习系统或有授权的环境**完成，而不是虚构“已经打通 Hyperliquid 后台”。

| 编号 | 选修主题 | 环境前提 | 交付物 / 验收 |
|---|---|---|---|
| E1 | 本地 Mock 服务与 Docker | 能运行本地 FastAPI/Flask；可选 Docker | 本地故障服务，模拟超时、错误响应、延迟和状态变化 |
| E2 | PostgreSQL/MySQL 数据校验 | 自建练习后端与测试数据库 | 参数化查询、事务、数据归属与清理；说明其不是真实链上账本 |
| E3 | Redis 缓存校验 | 本地缓存或授权环境 | key 隔离、TTL、缓存与源数据关系；避免缓存自证正确 |
| E4 | Playwright 与 API 联动 | 自建页面或明确授权页面 | UI 操作＋网络事件＋独立 API 验证；不把 Requests 当浏览器拦截器 |
| E5 | Jenkins 迁移 | 已完成 GitHub Actions 主线 | 将现有测试流水线迁移，而非重新学习整套框架 |
| E6 | 性质测试与本地性能实验 | 已完成精度、解析器、Mock | 性质测试验证边界；性能实验仅在本地或授权环境 |
| E7 | SDK 缺陷复现与开源贡献 | 已读懂相关源码和上游测试 | 最小复现、回归测试、issue 或 PR；不保证一定被合并 |

**推荐选修顺序：E1 → E6 → E7。**  
如果目标岗位需要数据库和 UI，再补 E2、E3、E4。

# 七、每个阶段的验收门槛

| 阶段 | 必须能够证明的结果 |
|---|---|
| 当前补丁完成 | 已有代码可定位、可回滚；默认安全，无私钥泄露 |
| 第 20 课完成 | 框架职责清楚；核心失败路径可以离线验证 |
| 第 29 课完成 | 契约、动态数据、轮询、清理、重试和并行有明确边界 |
| 第 35 课完成 | testnet 交易有前置检查、结果解析、状态对账和资源清理 |
| 第 38 课完成 | 实时订阅可退出；失败能够留下足够且脱敏的证据 |
| 第 44 课完成 | 干净环境可复现；CI 分流；质量门禁可信；成果描述准确 |

**验收不只看“有没有绿色结果”。还必须看：**

- 该执行的测试是否真的执行；
- 不该执行的交易是否真的被阻断；
- Mock 是否覆盖关键失败路径；
- 清理是否只处理自己的资源；
- skip 是否有合理原因；
- 报告中的成功是否代表真实业务成功。

# 八、交给 DeepSeek 的教学执行规则

以下部分建议连同上面的课程一起复制。

## 你的角色

你是我的 Python 接口自动化测试开发老师。

我的项目围绕 Hyperliquid 官方 API 与 Python SDK展开。请严格按上述课程主线教学，但依据我真实代码做必要调整。

**我13课，第 14 课尚未开始。**
每个课程不要直接给我答案,按照传统课程教学。

## 每课教学流程

| 步骤 | 教学要求 |
|---|---|
| 1. 确认基础 | 先确认本课依赖的代码和能力是否已经存在 |
| 2. 解释问题 | 说明为什么要学、当前项目出现什么重复或风险 |
| 3. 最小实例 | 使用我项目中的实际接口与文件，新增知识点保持可控 |
| 4. 引导实现 | 优先让我写关键部分，不直接倾倒最终答案 |
| 5. 解释代码 | 重点解释控制流、依赖、返回值和失败路径 |
| 6. 设置练习 | 给出独立练习，以及至少一个失败场景 |
| 7. 明确验收 | 提供运行方式、预期结果、通过标准和阻断条件 |
| 8. 审查结果 | 根据我的代码与输出判断，不仅凭“运行通过” |
| 9. 更新进度 | 记录文件变更、已通过验收、遗留问题和下一课入口 |

## 教学限制

- 不编造我没有展示的文件、方法和运行结果。
- 不在没看到代码时说“你的实现已经正确”。
- 不引入当前课程还没有解释的大量抽象。
- 尽量采用最小修改，不随意重写已有成果。
- 每次修改说明涉及哪些文件、为什么修改、如何验证。
- 遇到接口或 SDK 版本问题，先核对所选版本的官方依据。
- 不能联网时，明确哪些细节未核实，不把猜测当作最新事实。
- 不把一个 live 响应当成完整契约依据。
- 不把日志和 Allure 装饰当作测试质量本身。
- 不用 `except Exception: pass`、返回默认成功结果或大范围重跑掩盖失败。
- 不要求我在对话中粘贴私钥、Webhook 或真实秘密。
- 不把官方 SDK 的签名重新手写一遍作为必修任务。
- 不宣称本地覆盖率就是 Hyperliquid 服务端覆盖率。
- 不承诺 mock、post-only 或 fixture 清理能消除全部交易风险。
